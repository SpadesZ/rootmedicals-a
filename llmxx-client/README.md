# llmxx-client

This folder is the strict client-side boundary for the deliverable `rootmedicals-a` system.

## Structure

- `apps/thin-capture-client` - active client. It captures the HIS window, sends the
  screenshot to `llmxx-server`, and renders the result in the DoctorAlertWidget. It
  owns the Ctrl+Alt+G hotkey, the tray app and the client launch scripts.
  It deliberately does **no** OCR and no medical normalization: both run on
  `llmxx-server`, so the client stays thin.
- `apps/clinicalguard-standalone` - bundled ClinicalGuard mock HIS used for local
  end-to-end demos. It also writes the ICD sidecar
  (`data/current_icd_selection.json`) that the thin capture client reads.
- `legacy/qt-capture` - earlier Qt capture prototype kept for reference only.

The former `apps/local-ocr` tray client was removed when the client was thinned
out; what remains of it is `../legacy/client-local-ocr-legacy` (library modules,
reference only) and `../legacy/launchers` (dead double-click wrappers). Neither is
on the supported path.

## Entry Points

Two control panels exist; pick by what you are running.

Full local stack (server + client + RAG/LAVA), from the project root:

```powershell
cd "<rootmedicals-a>"
.\RootMedicals-Control.cmd
```

Client only, pointed at an already-deployed `llmxx-server` (this is the one that
ships in the `RootMedicals-HIS-Client-*.zip` delivery package):

```powershell
cd "<rootmedicals-a>\llmxx-client"
.\RootMedicals-Control.cmd
```

The client panel creates `apps/thin-capture-client/.venv` on first run, then
delegates to `RootMedicals-Control.ps1`. That script reads the backend address
from `apps/thin-capture-client/config/default_config.json` — note it reads
`default_config.json`, not the `.vm.json` / `.local.json` templates.

The panel shows a single start button, **Start Live RAG**. `LiveSynthetic` and
`DemoFixture` are mutually exclusive *server* states (set on the VM through
`LLMXX_DEMO_FIXTURE_MODE` / `LLMXX_RAG_DEMO_SYNTHETIC_FALLBACK`, then restart the
container); the client cannot switch them, so buttons for them only ever produced
an error dialog. Both remain reachable from the command line when a backend
really is in that mode: `.\RootMedicals-Control.ps1 -Action DemoFixture`.

## Building the delivery package

Run from the repo root:

```powershell
.\Build-ClientDelivery.ps1                 # uses the endpoint recorded in default_config.vm.json
.\Build-ClientDelivery.ps1 -BackendUrl "http://<host>:8000/api/intake"
.\Build-ClientDelivery.ps1 -WhatIfOnly     # assemble and check, produce no zip
```

It writes `RootMedicals-HIS-Client-<date>.zip` next to the repo. Three files in
that package do not exist in this repo and are generated by the script, which is
why the package cannot be reproduced by zipping the tree by hand:
`README-START-HERE.txt`, `Start-RootMedicals-HIS-Demo.cmd`, and the delivery
`default_config.json`.

That last one is the step worth knowing about. The repo keeps
`default_config.json` pointed at the local development backend
(`http://127.0.0.1:8017`), and the deployed address lives only in
`default_config.vm.json`. Packaging must copy the template over it. Miss that and
the client silently talks to localhost with no error shown to the user — the
2026-09-04 package shipped this way and pointed at a VM that no longer existed.
The script therefore refuses to build a package whose endpoint is a loopback
address, and re-opens the finished zip to confirm the endpoint, that no runtime
state leaked (`.venv`, `diagnostics`, ClinicalGuard's `data/` sidecar, which
contains the packager's last SOAP text), and that the control panel still has
exactly one start button.

Server-side entry points remain under `../llmxx-server`.
